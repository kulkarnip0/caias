UNIT II · PROCESS SYNCHRONIZATION

When many processes share one resource, who goes first?

Modern systems run many processes and threads concurrently. When two of them access the same shared data at the same time, the final result can depend on the exact order of execution. Process synchronization provides rules and mechanisms that coordinate this shared access so that data remains consistent.

Central question: How can several processes cooperate and share data without corrupting it?

1. Why do we need process synchronization?

Processes often cooperate

A process may produce information that another process consumes. Processes may share memory, files, buffers, counters, devices or database records. Sharing is useful—but it also creates a coordination problem.

Concurrent access can become inconsistent

If one process is changing a shared memory location while another reads or changes the same location, the second process may observe an incomplete or stale value. The outcome may change from one run to another.

Related illustration from Guru99: concurrent processes accessing shared data.

Think of a single attendance register: two teachers cannot safely erase and rewrite the same total at exactly the same time. The shared data is the register; synchronization controls access to it.

2. Race condition — the result depends on timing

A race condition happens when multiple processes or threads access shared data concurrently and the final result depends on the unpredictable order in which their individual instructions execute.

Process P1: increment

Read X = 5
Compute 5 + 1 = 6
Write X = 6

Process P2: increment

Read X = 5
Compute 5 + 1 = 6
Write X = 6
Expected: two increments should change 5 → 7. Possible unsynchronized result: both processes read 5 before either writes, so both write 6. One update is lost.

3. Four sections around shared access

A process that uses shared data is commonly described as moving through four logical sections. The important idea is that the critical section is protected by an entry protocol and followed by an exit protocol.

Entry Section
Ask for permission
→
Critical Section
Access shared data
→
Exit Section
Release permission
→
Remainder Section
All other work

Entry

Code that decides whether the process may enter the protected region. A lock acquisition or wait operation is typically placed here.

Critical

The part that reads or modifies shared data or resources. Correct synchronization prevents conflicting processes from being here together.

Exit

The process announces that it has finished using the shared resource and allows a waiting process to proceed.

Remainder

All code that does not require exclusive access to the shared resource.

4. What is the Critical-Section Problem?

Suppose there are processes P₀, P₁, …, Pₙ₋₁, and each sometimes executes code that accesses a shared resource. The operating system or synchronization algorithm must design an entry/exit protocol so that concurrent execution never causes inconsistent shared data.

SHARED DATA
counter / file / buffer / device

P1 wants access

P1 executes its entry section. If the resource is available, P1 enters the critical section and changes the shared data.

P2 arrives at the same time

P2 must not enter a conflicting critical section while P1 is inside. It waits until P1 completes its exit section.

do {
    entry section

    critical section   // access shared data

    exit section

    remainder section
} while (true);

5. A correct solution must satisfy three requirements

01

Mutual Exclusion

If one process is executing in its critical section, no other process that uses the same protected resource may simultaneously execute its conflicting critical section.

Meaning: at most one process inside at a time.

02

Progress

If no process is in the critical section and one or more processes want to enter, the decision about who enters next must not be postponed forever.

Meaning: an empty critical section should not remain unnecessarily blocked.

03

Bounded Waiting

After a process requests entry, there must be a limit on how many times other processes may enter before that waiting process gets its turn.

Meaning: no starvation.

Memory trick: Mutual Exclusion = safety, Progress = somebody can move, Bounded Waiting = everybody eventually gets a fair chance.

6. How can we solve the critical-section problem?

There is no single mechanism used in every situation. Operating systems use software algorithms and atomic hardware support to build synchronization primitives.

Software algorithms

Algorithms such as Peterson’s solution demonstrate how shared variables can coordinate two processes and satisfy the critical-section requirements under the classical model.

Hardware support

Processors provide atomic instructions that allow the OS to implement locks safely. Atomic means the operation appears indivisible: another processor cannot observe it half-completed.

Mutex locks

A process acquires a lock before entering the protected region and releases it afterward. Another process attempting to acquire the same lock must wait.

Semaphores

A semaphore is a synchronization variable operated through atomic wait and signal operations. Semaphores can coordinate both mutual exclusion and more general ordering between processes.

7. First look at Peterson’s Solution

Peterson’s solution is a classic software solution for two processes. It uses two ideas: an interest flag showing that a process wants to enter, and a turn variable that resolves the case where both want to enter at once.

Related Peterson-solution illustration from Guru99.

// Conceptual form for process i, where j is the other process
flag[i] = true;     // I want to enter
turn = j;           // give the other process priority if both compete

while (flag[j] && turn == j) {
    ;               // wait
}

// CRITICAL SECTION

flag[i] = false;    // I am leaving
Important: Peterson’s algorithm is mainly valuable for understanding the logic of mutual exclusion, progress and bounded waiting. The next lesson can examine it line by line and then move to hardware instructions, mutex locks and semaphores.
