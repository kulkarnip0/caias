UNIT II · CLASSIC SYNCHRONIZATION

Classic Problems of Synchronization & Monitors

Synchronization becomes much easier to understand when we watch processes compete and cooperate around real shared resources. Three classic problems expose the main difficulties: bounded buffer, readers–writers, and dining philosophers. Then monitors show a higher-level way to organize the same coordination.

Start from basicsBounded BufferReaders–WritersDining PhilosophersMonitors

1. WHAT is a synchronization problem?

Imagine several processes running independently. If each process uses only its own data, there is little conflict. The interesting case begins when they share something: a buffer, file, database, printer, counter, or other limited resource.

WHAT can go wrong?

Two operations can overlap in an unsafe order. A process may use data before it exists, overwrite data that has not been consumed, modify data while another process reads it, or wait forever for a resource.

WHY synchronize?

We need rules that decide who may proceed now, who must wait, and when a waiting process may continue. Mutual exclusion alone is not always enough; processes often need ordering and signalling too.

Big idea: synchronization is not merely “locking everything.” It is coordinating concurrent actions so that shared state remains correct and useful progress continues.

2. Bounded Buffer — Producer & Consumer

WHAT?

A producer creates items and places them into a shared buffer. A consumer removes those items. The buffer has only N slots, so it can become full or empty.

WHY is synchronization needed?

The producer must not insert into a full buffer. The consumer must not remove from an empty buffer. Also, while the shared buffer structure is being changed, another process must not simultaneously corrupt that update.

3. Readers–Writers Problem

WHAT?

Several processes share one data set. A reader only observes the data. A writer can modify it. Reading does not change the shared state, so several readers can normally read together. Writing is different: a writer needs exclusive access.

WHY is it difficult?

If every reader takes an exclusive lock, safe parallel reading is unnecessarily lost. But if writers are allowed to enter while readers are active, a reader can observe partially changed data. Priority also matters: continuously arriving readers can make a writer wait indefinitely, while strict writer priority can delay readers.

Core rule: many readers may coexist, but a writer must be alone. A complete design must also think about fairness and starvation.

4. Dining Philosophers — Resource Allocation

WHAT?

Five philosophers sit around a circular table. Between every neighboring pair is one chopstick. Each philosopher alternates between thinking and eating. To eat, a philosopher needs the two adjacent chopsticks.

WHY is this a famous synchronization problem?

Suppose all five become hungry at once. Each picks up the chopstick on the left. Now everyone holds one resource and waits for the other resource. Nobody can continue, and nobody releases what they already hold. This is deadlock.

Deadlock picture: P1 waits for P2's resource → P2 waits for P3 → P3 waits for P4 → P4 waits for P5 → P5 waits for P1. The wait forms a circle.

Common ways to break this situation include allowing at most four philosophers to compete at once, acquiring both chopsticks together, or using an asymmetric order so that not everyone requests resources in the same direction. Removing deadlock does not automatically guarantee freedom from starvation.

5. Monitors — Put the Rules Around the Shared Data

WHAT is a monitor?

A monitor is a high-level synchronization construct that groups shared data together with the procedures that are allowed to access it. The key protection rule is simple: only one process can be active inside the monitor at a time.

WHY do we need condition variables?

Mutual exclusion answers “who may be inside?” But sometimes a process is inside and discovers that it cannot continue yet. For example, a consumer enters a buffer monitor but the buffer is empty. It should not keep holding the monitor and block everyone else.

wait()

x.wait() suspends the calling process on condition x and releases the monitor so another process can enter and change the state.

signal()

x.signal() indicates that the condition may now be satisfied and allows a process waiting on x to resume according to the monitor's scheduling semantics.

monitor BoundedBuffer { item buffer[N]; condition notFull, notEmpty; insert(item x) { if buffer is full: notFull.wait(); add x to buffer; notEmpty.signal(); } remove() { if buffer is empty: notEmpty.wait(); remove an item; notFull.signal(); } }
Mental model: a semaphore exposes explicit counters and wait/signal operations. A monitor wraps the shared state and permitted operations into one protected abstraction, while condition variables express reasons for waiting.
