UNIT II · AFTER PROCESS SYNCHRONIZATION

Hardware Synchronization

We already know the problem: two processes can reach shared data at nearly the same time. Now we ask a new question: can the CPU itself give us an operation that cannot be split in the middle? That is the central idea behind hardware synchronization.

01 · FIRST UNDERSTAND THE NAME

Why is it called a “hardware” solution?

Peterson's solution is a software protocol: processes cooperate using shared variables such as flag[] and turn. Hardware synchronization takes a different route. It relies on a capability supplied by the processor: a special read/modify/write operation can be performed atomically. Other processes or CPUs cannot slip another conflicting operation into the middle of that atomic action.

The word hardware does not mean that the entire synchronization algorithm is a physical circuit. The program still contains entry/exit code and a lock variable. The crucial operation that makes the lock safe is guaranteed atomic by CPU/hardware support.

🚪 Real-life analogy: one key, one door

Imagine a laboratory with one physical key. Checking whether the key is available and taking it must behave like one indivisible action. If two students can both see “key available” before either takes it, both may believe they own it. Atomic hardware instructions make the “check + take” operation behave as one action.

🎟️ Ticket counter analogy

Two people ask for the last ticket. A safe machine must not do “check = 1 ticket” for both and only later decrement it. The check-and-update must be indivisible. Hardware synchronization gives software primitives from which such locks can be built.

02 · THE KEY WORD

Atomicity: “all at once” from other CPUs' point of view

Consider the naïve lock below. It looks reasonable, but checking lock and changing lock are separate actions. A context switch can occur between them.

Unsafe: two separate steps

if (lock == false) {   // STEP 1: check
    lock = true;       // STEP 2: set
    // critical section
}

P1 may check false, get interrupted, then P2 also checks false. Both can believe they acquired the lock.

Hardware idea: indivisible operation

old = TestAndSet(&lock);
// read old lock AND set lock=true
// as ONE atomic instruction

No competing process can observe the operation halfway through. If P1 wins, P2 sees the already-set lock.

03 · HARDWARE ALGORITHM 1

Test-and-Set

TestAndSet examines the current lock value, stores that old value for the caller, and sets the lock to true—atomically. If the returned old value is false, the caller discovered an unlocked lock and simultaneously claimed it. If the returned value is true, somebody already holds the lock, so the caller spins.

Atomic instruction

boolean TestAndSet(boolean *target) {
    boolean old = *target;
    *target = true;
    return old;
}

Think of these lines as the meaning of one atomic hardware-supported operation—not as ordinary interruptible application statements.

Process entry and exit

while (TestAndSet(&lock))
    ;                 // busy waiting

// CRITICAL SECTION

lock = false;         // release

✓ Mutual exclusion   ✓ Progress   ✗ Bounded waiting not guaranteed

Why the “strange” while condition? First process: old lock = false → TestAndSet returns false → while(false) ends → enter. Second process: old lock = true → returns true → while(true) keeps spinning.

🚻 Real-life example: occupied indicator

Think of a single-person room. The first person atomically changes the indicator from FREE → OCCUPIED and enters. Everyone arriving afterward sees OCCUPIED. Test-and-Set is stronger than merely looking at the sign: looking and claiming happen as one indivisible operation.

04 · HARDWARE ALGORITHM 2

Swap

Swap is another hardware-lock technique. Each process has a local key, while lock is shared. An atomic Swap exchanges the values. A process starts with key=true; when it swaps with a free lock=false, the shared lock becomes true and its key becomes false. That false key lets it leave the waiting loop and enter.

Atomic swap

Swap(&lock, &key);
Before
lock=false
key=true
⇄
After
lock=true
key=false

Entry idea

key = true;
while (key == true)
    Swap(&lock, &key);

// CRITICAL SECTION

lock = false;

Like simple Test-and-Set, mutual exclusion is achieved, but a waiting process has no guaranteed turn; starvation is possible.

🏷️ Real-life analogy: exchanging tags

The door owns a FREE tag and you hold an WANT-TO-ENTER tag. The atomic swap exchanges the tags in one motion. After the exchange, the door carries the occupied state and you carry the value that tells you whether you succeeded.

05 · HARDWARE ALGORITHM 3

Unlock-and-Lock: add bounded waiting

A weakness of basic Test-and-Set and Swap is fairness: when the lock becomes free, any spinning process may win again. A bounded-waiting form improves this by keeping a waiting[i] state for processes and selecting the next waiting process in circular order. On exit, a process hands permission toward the next waiter instead of simply making the competition completely open again.

Main improvement: waiting processes are considered in an ordered/circular manner. This is why this form can provide bounded waiting, unlike the simple Test-and-Set and Swap versions described above.

🏥 Real-life example: token queue

A doctor does not throw the room key into a crowd after each patient. The next waiting token is called. The important idea is not merely locking the room, but controlled hand-off, so one unlucky person cannot be bypassed forever.

06 · IMPORTANT RELATED CPU PRIMITIVE

Compare-and-Swap (CAS)

Another common atomic instruction is Compare-and-Swap. It compares the current memory value with an expected value. Only if they match does it replace the memory value with a new value. The comparison and possible update form one atomic action.

Concept

old = CompareAndSwap(&lock, 0, 1);

// Conceptually:
// if lock == expected(0)
//     change lock to new value(1)
// return old value

For a lock

lock = 0: process expects 0 and requests 1 → match → lock becomes 1 → process acquires it.

lock = 1: expected 0 does not match → lock stays 1 → process waits/spins.

✓ Mutual exclusion   ✓ Progress   ✗ Basic form does not ensure bounded waiting

🏨 Real-life analogy: reserve only if still available

You say, “Reserve room 205 only if its status is still AVAILABLE; if so, change it to RESERVED.” The check and status change must happen together. If somebody else reserved it first, your expected value no longer matches and your update fails.
