07 · OS UNIT I

Multithreaded Programming — see how threads map to the kernel.

A thread is a lightweight unit of CPU execution inside a process. This lesson focuses on what threads share, what they keep separately, why multithreading helps, and how user threads map to kernel threads in the major threading models.

01 · THREAD CONCEPT

One process can contain many threads

A process owns resources such as its address space and open files. Threads are execution paths inside that process. Threads of the same process share many process resources, but each thread needs its own execution state.

Shared by threads of one process

CodeData / HeapOpen filesAddress space

Private to each thread

Program counterRegistersStackThread ID
Remember: a process is the resource container; a thread is a unit of execution inside it.

Single-threaded process

Only one execution path exists. If it waits for a blocking operation, the process may stop doing useful work until that operation completes.

Multithreaded process

Several execution paths exist in the same process. While one thread waits, another may continue, and on multicore processors multiple threads may run in parallel.

02 · WHY MULTITHREADING?

Four classic benefits

Responsiveness

Part of an application can continue running while another thread waits, keeping the program responsive.

Resource sharing

Threads naturally share the process address space and files, making communication cheaper than communication between separate processes.

Economy

Creating and switching threads is generally cheaper than creating and switching full processes because less state must be managed.

Scalability

Independent threads can execute simultaneously on different CPU cores, allowing an application to exploit multicore hardware.

03 · USER THREADS AND KERNEL THREADS

Who knows about the thread?

User-level threads

Managed by a user-space thread library. Creating and switching them can be fast because the kernel may not be involved in every thread operation.

Limitation: in a many-to-one design, the kernel sees only one schedulable entity for the process.

Kernel-level threads

Known and scheduled by the operating system kernel. The kernel can schedule different threads of the same process independently and across multiple cores.

Cost: management usually involves kernel support and therefore more overhead than a purely user-level operation.

06 · MODEL COMPARISON

What changes from one model to another?

ModelMappingBlocking effectParallelism on multicoreMain trade-off
Many-to-OneMany user → one kernelOne blocking kernel call can block the whole processNo true parallelism for those user threadsLow management overhead, poor concurrency
One-to-OneEach user → one kernelOther threads can continueYesGood concurrency, more kernel-thread overhead
Many-to-ManyMany user → many kernelBlocking of one kernel thread need not stop all user threadsYes, up to available kernel threads and coresFlexible but more complex
Two-LevelMany-to-many plus optional bindingSimilar to many-to-many; selected user threads can be boundYesAdds control by allowing selected bindings
Quick memory aid: Many-to-One is simplest but restrictive; One-to-One exposes maximum kernel scheduling; Many-to-Many tries to balance flexibility and overhead; Two-Level adds optional binding.
