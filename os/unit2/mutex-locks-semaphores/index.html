UNIT II · AFTER HARDWARE SYNCHRONIZATION

Mutex Locks & Semaphores

We now move from low-level atomic hardware instructions to the synchronization tools programmers and operating systems actually use. As always, we begin with what they are, then ask why we need them.

01 · WHAT?

What are Lock, Mutex and Semaphore?

All three are synchronization primitives: tools used to control how concurrent threads or processes access shared resources. Their job is to prevent unsafe interference, but they do it in different ways.

🔒 Lock

A lock is a gatekeeper for a shared resource. A thread tries to acquire it before entering the critical section and releases it afterward. If the lock is already held, another thread must wait.

🧷 Mutex

Mutex means mutual exclusion. In the CodeGenes framing, it is a lock with strict ownership: the thread that locks the mutex is the thread that must unlock it.

🚦 Semaphore

A semaphore stores a count. That count represents how many permits/resources are available. A counting semaphore may allow several threads through at the same time; a binary semaphore uses only 0 and 1.

First big distinction: a lock/mutex usually protects one critical section so only one owner enters, while a counting semaphore can represent N available resources. A binary semaphore can behave similarly to a one-permit gate, but unlike a mutex it does not inherently require the same thread to signal it.
02 · WHY?

Why do we need these if hardware synchronization already exists?

In the previous topic, the CPU gave us atomic operations such as Test-and-Set and Compare-and-Swap. Those are excellent building blocks, but programmers do not want to manually design a correct spin protocol every time shared data must be protected.

A higher-level primitive gives a clearer contract: “only one thread at a time,” “only the owner may release,” or “allow up to three users.” It can also let waiting threads block instead of wasting CPU cycles in a busy-wait loop.

🏦 Shared bank balance

Two threads update the same account. Without synchronization, both may read the old balance and overwrite one another. A lock or mutex protects the update as a critical section.

🖨️ Three identical printers

If a lab has three printers, we do not want a mutex that permits only one print job. A counting semaphore initialized to 3 naturally models the three available printer permits.

03 · LOCK

Lock: the basic gate

The source describes a lock as the simplest mutual-exclusion primitive. Its two basic operations are Acquire and Release. Acquire succeeds immediately if the lock is free; otherwise the caller waits. Release makes it available again.

acquire(lock);

// CRITICAL SECTION
shared_counter++;

release(lock);

Reentrant vs non-reentrant lock

A non-reentrant lock cannot safely be acquired twice by the same thread; doing so can make the thread wait on itself. A reentrant/recursive lock remembers ownership and an acquisition count, allowing the same thread to acquire it again and requiring matching releases.

04 · MUTEX

Mutex: mutual exclusion + ownership

🚗 Real-life analogy: one car key assigned to a driver

A lock says, “the car is in use.” A mutex adds, “T1 is the owner of this key right now.” Another person cannot simply declare the car free while T1 is still driving it. Ownership is the crucial difference emphasized in the reference.

05 · COUNTING SEMAPHORE

Semaphore: a counter of permits

A semaphore is more flexible because it represents a number of available permits. The two classic operations are wait (P) and signal (V). Wait consumes a permit; if none is available, the caller blocks. Signal returns a permit and may wake a waiting caller.

wait(S);      // take one permit

// use one of the limited resources

signal(S);    // return one permit
Example: if S = 3, at most three threads may be inside the semaphore-controlled region at once. The fourth must wait until somebody signals.

06 · BINARY SEMAPHORE

Binary semaphore: 0 or 1, often useful for signaling

A binary semaphore has only two useful count states, 0 and 1. It can look mutex-like, but the source highlights a key distinction: it has no strict ownership requirement. That makes it especially useful for signaling between different threads.

Producer

produce_data();
signal(ready);

The producer may signal that data is ready.

Consumer

wait(ready);
consume_data();

The consumer can start first and block until another thread signals.

Choose Lock

Use a simple mutual-exclusion gate around one shared resource when the API's lock semantics are sufficient.

Choose Mutex

Use when one thread must clearly own the critical section and only that owner should release it.

Choose Semaphore

Use when there are N permits/resources, or when one thread needs to signal another thread.

Exam memory trick: Lock = gate. Mutex = gate + owner. Semaphore = permits.

Common mistakes

Holding locks for too long reduces concurrency. Forgetting to release a primitive can block others indefinitely. Acquiring multiple locks in inconsistent order can cause deadlock. The source also notes priority inversion as an important mutex concern in priority-based systems.
