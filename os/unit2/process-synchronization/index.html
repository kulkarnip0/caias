UNIT II · PROCESS SYNCHRONIZATION

When many processes share one resource, who goes first?

Modern systems run many processes and threads concurrently. That is efficient, but when two execution streams touch the same shared data, the final answer can depend on timing. Process synchronization gives us rules and mechanisms to coordinate access and keep data correct.

Central question: How can several processes cooperate and share data without corrupting it?

1. Why process synchronization?

Processes cooperate

Processes may share memory, files, counters, buffers, devices, queues or database records. Sharing lets work move quickly between processes, but it also means one process can interfere with another if their operations overlap.

Concurrency creates timing uncertainty

The CPU may interrupt one process between two instructions and run another. On a multicore processor, two threads may truly execute at the same time. Therefore, a simple statement such as counter++ should not automatically be imagined as one indivisible action.

Two processes can reach the same shared resource. Synchronization controls the order of access.

Classroom analogy: imagine one attendance total written on a board. If two people both read 45 and each independently adds one, both may write 46. The correct final value should be 47.

2. Race condition — timing changes the answer

A race condition occurs when the result of concurrent execution depends on the particular order in which processes or threads perform their operations. The most useful way to understand it is to break a seemingly simple update into smaller steps.

3. Four sections of a synchronization solution

A process that accesses shared data can be viewed as moving through four logical sections. The entry and exit sections act like the doorway around the protected critical section.

Entry section

Code that requests permission to enter. A lock acquisition, semaphore wait, or software protocol belongs here.

Critical section

The part that reads or changes the shared resource. Conflicting processes must not execute here together.

Exit section

Code that announces completion and releases the synchronization mechanism.

Remainder section

Everything else. No exclusive access to the protected shared resource is needed here.

4. The Critical-Section Problem

Suppose P0, P1, …, Pn−1 all have code that sometimes accesses shared data. We need an entry/exit protocol that lets them run concurrently while preventing unsafe overlap in the critical section.

do {
    entry section

    critical section      // access shared data

    exit section

    remainder section
} while (true);
The goal is not to stop concurrency. Processes should still execute independently whenever possible. We only restrict the small region where simultaneous access can cause an incorrect result.

5. Three requirements of a correct solution

01

Mutual Exclusion

If one process is in its critical section, no other process using the same protected resource may be inside a conflicting critical section at the same time.

Think: only one inside.

02

Progress

If the critical section is empty and processes want to enter, the decision about who enters next must not be postponed forever by processes that are not interested.

Think: an empty room should not stay blocked.

03

Bounded Waiting

After a process requests entry, there must be a finite limit on how many times others can enter before it gets its chance.

Think: no starvation.

7. Peterson’s Solution — software coordination for two processes

Peterson’s solution is a classic two-process software solution. It uses two flag variables to record interest and a turn variable to break a tie when both processes want to enter.

// Process Pi, where Pj is the other process
flag[i] = true;          // I want to enter
turn = j;                // if both want it, let the other go first

while (flag[j] && turn == j) {
    ;                    // wait
}

// CRITICAL SECTION

flag[i] = false;         // I am leaving

8. Recap — build the mental model

Race condition

Outcome depends on timing/interleaving of concurrent operations.

Critical section

Small protected region that accesses shared data.

Correctness

Mutual exclusion + progress + bounded waiting.

Mechanisms

Software algorithms, atomic hardware, mutexes and semaphores.
