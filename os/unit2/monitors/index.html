UNIT II · MONITORS

Monitors — Synchronization as a Protected Abstraction

A monitor combines shared data, the operations that may use that data, automatic mutual exclusion, and condition-based waiting into one organized synchronization structure.

Start from WHATWHY monitors?Structurewait() & signal()Bounded BufferInteractive Simulator

1. WHAT is a Monitor?

Suppose several processes or threads share one object, such as a buffer. We already know that uncontrolled simultaneous access can create race conditions. One approach is to scatter lock and semaphore operations throughout the program. A monitor takes a more structured approach.

Monitor = shared data + procedures that operate on it + synchronization rules.

The shared data is kept inside the monitor. Code outside the monitor does not directly manipulate that protected state; it requests an operation through a monitor procedure. The monitor guarantees mutual exclusion: at most one thread or process executes inside the monitor at a time.

Process P1
→
Monitor procedure
→
Protected shared data

If P1 is executing a monitor procedure and P2 calls another procedure of the same monitor, P2 cannot enter the protected monitor body simultaneously. It waits until monitor access becomes available.

2. WHY do we need Monitors?

Low-level synchronization primitives are powerful, but correctness depends on using them in the right places and in the right order. A missing unlock, an incorrect semaphore operation, or an unsafe access outside the critical section can break synchronization.

Without a monitor

The synchronization protocol is often spread across many pieces of code. Every caller must remember how and when to protect the shared state.

With a monitor

The shared state and the rules for accessing it are packaged together. Mutual exclusion is part of the abstraction rather than a rule every caller must manually reproduce.

Main benefit: monitors make synchronization easier to reason about because access to shared state follows a controlled interface.

The first two parts give us protected state and operations. But mutual exclusion by itself does not solve every synchronization problem. Sometimes the process that successfully enters the monitor discovers that the operation is not yet logically possible.

Example: a consumer enters a buffer monitor, but the buffer is empty. It owns monitor access, yet there is nothing to consume. It must wait for the state to change.

4. Condition Variables — Waiting for the Right State

A condition variable represents a reason why execution may need to wait. Typical names such as notEmpty and notFull make the required state easy to understand.

x.wait()

The calling process cannot continue because condition x is not satisfied. It is suspended in the waiting queue associated with x. Crucially, it gives up monitor access so another process can enter and change the shared state.

x.signal()

A process has changed the shared state in a way that may allow a process waiting on condition x to continue. The signal makes an appropriate waiter eligible to resume according to the monitor's scheduling semantics.

Why must wait() release the monitor?

Imagine a consumer finds an empty buffer and waits while still occupying the monitor. The producer would need to enter the same monitor to insert an item, but it could not enter. The consumer would wait for an item that the producer is prevented from producing. Therefore a condition wait must suspend the caller and release monitor ownership.

These two kinds of waiting are easy to confuse.

Condition-variable queueIt entered, checked the shared state, and discovered that a required condition is not satisfied.Another process changes the state and signals the relevant condition.
Remember: “I cannot enter yet” and “I entered, but cannot continue yet” are different situations.

6. Bounded Buffer Using a Monitor

Consider a buffer with N slots. The producer calls insert(); the consumer calls remove(). The monitor automatically protects the buffer so only one of these procedures changes it at a time.

monitor BoundedBuffer { item buffer[N]; int count = 0; condition notFull, notEmpty; procedure insert(item x) { while (count == N) notFull.wait(); add x to buffer; count = count + 1; notEmpty.signal(); } procedure remove() { while (count == 0) notEmpty.wait(); remove an item; count = count - 1; notFull.signal(); } }
Buffer full?

Producer waits on notFull.

Buffer empty?

Consumer waits on notEmpty.

Buffer changed?

The relevant condition is signalled so waiting work can resume.

The use of while expresses an important idea: when execution resumes, the condition should be checked again before relying on the shared state.

The producer moves to the notFull condition queue and releases the monitor. A consumer can now enter, remove an item, decrement count, and call notFull.signal(). The waiting producer can later regain monitor access, check the condition again, and insert its item.

This is the heart of a monitor: mutual exclusion controls simultaneous access; condition variables coordinate when an operation is allowed to continue.

9. Monitor vs Mutex vs Semaphore

MechanismMain ideaWhat the programmer thinks about
MutexExclusive ownership of a critical section/resourceLock and unlock around protected work
SemaphoreCounter/signalling synchronization primitiveExplicit wait/signal protocol and counts
MonitorProtected shared state + procedures + condition waitingOperations on the abstraction and conditions required for progress

A monitor is not simply another name for a mutex. Mutual exclusion is one property of a monitor, while the monitor also organizes the protected data and operations and can provide condition-based waiting.

10. Advantages and Limitations

Advantages

Synchronization rules stay close to the shared data. Automatic mutual exclusion reduces accidental concurrent access. Condition variables express waiting in terms of meaningful program state. The result is generally more structured and maintainable than scattered low-level synchronization.

Limitations

Incorrect condition logic can still cause blocking, starvation, or deadlock. Monitor semantics differ across languages and systems, so details of signalling and scheduling matter. Synchronization also introduces runtime overhead and can reduce concurrency when protected sections are too large.

11. Final Mental Model

ONE AT A TIME

The monitor provides mutual exclusion for its protected operations.

WAIT FOR STATE

A condition variable lets an operation sleep without blocking the monitor.

SIGNAL CHANGE

After changing shared state, an operation can wake work waiting for that condition.

In one sentence: a monitor is a protected home for shared state where only one execution is active at a time, and condition variables allow that execution to step aside when the state is not yet suitable.
